# Build 4 evidence: GitHub Copilot CLI

28 and 29 Oct 2026. Spec: `docs/requirements/r1a/build-4-copilot-adapter.md` in the private codehere repo. Requirements AGT-1, AGT-3, AGT-4.

Every Copilot run below used Copilot CLI 1.0.105, installed into a scratch folder (not globally), with its own `COPILOT_HOME` and a local model (Qwen 3.5 9B through Ollama, set in that folder's `providers.json`). No GitHub login was used. The developer's own `~/.copilot` was not read or changed.

## What Copilot CLI does

Three probe runs in a scratch repo with logging hooks in both `.github/hooks/probe.json` and `.claude/settings.json`:

- Copilot ran every hook from both files: 16 calls for 8 events. So Codehere's Claude Code hooks already ran under Copilot on beta.2.
- `COPILOT_CLI=1` is set for every hook; `COPILOT_HOOK_DIR` only for hooks from `.github/hooks/`. Inputs from the Claude file are in snake_case and carry a `timestamp`, which Claude Code's and Codex's inputs do not.
- A failed `npm test` arrives as a successful tool call (`postToolUse`, `resultType: "success"`) whose output ends with `<shellId: 0 completed with exit code 1>`.
- From Copilot's own file, `sessionStart` JSON `additionalContext` reached the model (it is in the requests in Copilot's debug log), `postToolUse` `additionalContext` was appended to the tool output, and an `agentStop` block's `reason` became the next user message, which the model followed. From the Claude file, plain text and Claude's `hookSpecificOutput` were ignored. `systemMessage` appeared nowhere.
- The processes above a hook were `copilot < node < shell`; `ps` worked.
- Copilot's session record is `COPILOT_HOME/session-state/<id>/events.jsonl`.

The inputs are saved in `test/fixtures/payloads/copilot-cli-1.0.105.jsonl`.

## How it is built

`codehere init --agent copilot` writes `.github/hooks/codehere.json` in Copilot's format. Under Copilot, a Codehere hook started from `.claude/settings.json` stays quiet when that file runs Codehere for the same event, so nothing runs twice; otherwise it answers in Copilot's format, so a team that never installed the Copilot file keeps the finish check.

## Review (28 Oct)

Codex is out of usage until 17 Nov 2026. A reviewer agent with no build notes read the diff, the spec and Copilot's docs, ran the suite and its own probes, and found:

1. **High.** The rule that silenced the Claude Code hooks under Copilot also removed the finish check that beta.2 gave Copilot users in repos with only those hooks, and anyone could silence Codehere for Copilot users by deleting or editing `.github/hooks/codehere.json`. Fixed: the Claude Code hooks stay quiet only for an event the Copilot file runs; otherwise they answer in Copilot's format.
2. **Medium.** The README promised lines that Copilot never shows. Fixed in Known limits.
3. **Medium.** Only `codehere.json` was protected, though Copilot runs every file in `.github/hooks/`. Fixed: the folder counts as one protected setting. Whether Copilot reloads hooks mid-session was unchecked; it does not (below).
4. **Low.** VS Code-format inputs lost their fields; `.github/hooks/` counted as code; the cloud agent note; test gaps (merging into an existing Copilot file, `settings.local.json`, non-hook settings). All fixed or covered.

The first run of 28 Oct gave L3 BLOCKED: for Copilot the wrapper captured every command's output, so `codehere approve` had no terminal and refused, and the script's setup check missed it ("not approved on this machine" contains "approved on this machine"). With no approved command, Codehere showed ⊘ and ran nothing, as designed. The wrapper now logs hook calls only, and the setup check looks for "· approved on this machine".

The hosted run used a GitHub login with Copilot's built-in MCP servers turned off (`--disable-builtin-mcps`), so the model could not call GitHub's API. The account offers no model by name (`model_picker_enabled` is false for every model in its catalog, and `--model gpt-6-luna` is refused), so the run used `--model auto`; every request in the debug log went to gpt-6-luna. Copilot's session records count 1 and 2 premium requests for its two sessions. Its first run gave L1 FAIL although the rules were in the first request: with this model Copilot logs requests in the Responses format, where the text is under `"text"`, and the script only read `"content"` lines. The script now reads each logged "Wire request" entry whole. On the logs already on disk it finds the rules in the hosted run and in two local runs, and not in a session without Codehere's hooks. The re-run is the row above.

In the first three result files the path to the scratch copy of Copilot is shortened to `<scratch>/copilot`; the script now writes only the file name.

## Copilot's hook file deleted mid-session (review finding 3)

On the scratch repo the final run left, `.github/hooks/codehere.json` was deleted from outside right after Copilot's session-start hook ran (session 5543d9ea, 29 Oct 07:06):
- **Copilot keeps the hooks it loaded.** It still called `codehere hook stop --agent copilot` at each stop.
- **The Claude Code hooks acted too**, since the file they check for was gone, so each stop ran Codehere twice. The agent was sent back twice, with one reason each time: first the failed tests, then the request to fill in a lesson. At the first stop the hook from the deleted file did send the agent back for the settings change (the session state records it), but Copilot passed on only the other hook's reason, so the agent never saw that one.
- Codehere was not silenced. The double run lasts only for that session: a new session no longer loads the deleted file.
