# What the finish check's ✓ promises

Written 19 Nov 2026 after L13 round 6, and bounded after round 8: Ega chose option A in the Pareto review (`docs/launch/PARETO_2026-11-19.md` in the codehere repo). A review checks the code against this promise, not against everything git can do.

## Who the adversary is

An agent trying to finish its task, doing what agents do while they work. Codehere checks that agent's work. It is not a sandbox against an agent that sets out to defeat Codehere itself, through git's own machinery or by editing Codehere's installed code. What Codehere catches of that kind today it keeps catching, but a way around it is a known limit, not a hole in this promise.

## The promise

Codehere prints ✓ only when all of these hold for the session:

1. Codehere ran the approved test command itself, at the end of the agent's turn, it passed, and, where Codehere can read the runner's count (node, jest, vitest, pytest, mocha, unittest, cargo), at least one test passed. Where it cannot, the ✓ line says "exit 0" instead of a count.
2. Every test file, test config, test setup file and CI file whose bytes changed since the session started was read by the weakened-test scan, and the scan found nothing.
3. No such file was touched while the check ran (between reading the record and the end of the test run): what ran must be what was read.

A test file is code in a test folder or with a test name, in a language the scan reads (`EXT_LANG` in `v2/src/noskip.js`); data in a test folder is not one. Test configs, setup and CI files are the ones `isCheckFile` in `v2/src/signals.js` names; CI files count at the repo's top, where CI reads them, so one moved elsewhere is a CI file removed. In `package.json`, the `test` script counts, and so does any `test:*` script something can run: another script names it or holds a glob (`run-s test:*`), or the approved command names it. pytest's config files are `pytest.toml`, `.pytest.toml`, `pytest.ini`, `.pytest.ini`, `pyproject.toml`, `tox.ini` and `setup.cfg`. In `tox.ini`, a pytest command's arguments in `commands` count too when the approved command names tox as a command word (`make test` that runs tox does not); `tox.toml` and `[tool.tox]` in `pyproject.toml` are not read for commands. A test config is read whole: what it tells the runner to leave out at session start is compared with what it tells it now, each value counted by the places that set it (a path one jest project ignores, added to another project, is new), so how its lines are wrapped, sorted or commented does not count; where the file read does not match the change (a file over 1 MiB, or one changed since), it is read line by line. When Codehere is set up in a subfolder of the repo, the test configs and setup files in each folder above it (a link counts by the file it points to), and the CI files at the repo's top, are recorded and read too; the subfolder's own `.github/workflows` is not the repo's CI. Test files outside Codehere's folder (a sibling package, a `tests/` folder at the repo's top) are not recorded: set Codehere up where the approved command's tests live. CI files are the names each service reads by default: `.github/workflows/*.yml` or `.yaml`, `.gitlab-ci.yml`, `.circleci/config.yml`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`. Not test configs, and so not covered: `vite.config.*` (where a vitest `test:` block can live), GitLab `include:` files, and GitHub composite actions (`.github/actions/*/action.yml`). Cypress specs (`*.cy.js`, `*.cy.ts`) are not test files.

"Changed" is decided by Codehere's own record of each such file's bytes, taken at session start and kept when a session resumes. Test files are read through that record, from their start version to their bytes now; other files through git's diff, with Codehere's own settings whatever the repo's config says (no external diff program, textconv, color, replace objects, fsmonitor or repo hooks). To build a diff from the record, Codehere writes the start version of a file that was changed or untracked at session start into git's object store, where git can later prune it. If a change cannot be read, there is no ✓ and the line says so.

## What the agent may do, and the promise must still hold

The things agents do while working on a task:

- Edit, add, delete, rename or move any file, with git or without it, and leave it unstaged or untracked, or ignored when a build or an install puts it there. Hiding a test file from git is not on this list: it is working against Codehere (below).
- Stage, commit, amend, stash, reset, check out, switch branches, rebase.
- Run the tests, build the project, install packages (into `node_modules`, a virtual environment or a build folder).
- Start a worktree inside the repo.

## Out of scope

A review that finds one of these should name it as out of scope, not as a hole in the promise.

- **Working against Codehere through git's machinery:** index flags (assume-unchanged, skip-worktree, sparse-checkout), replace refs, `core.bare` and `core.worktree`, filters and attributes set to hide a change, repo hooks, moving `.git`, a folder made only to stop the record walking (an empty `.git` or `pyvenv.cfg` beside the tests), or a test folder swapped for a link. The record catches many of these today; a way around it is a known limit.
- **Working against Codehere directly:** putting a test file where git ignores it, or adding an ignore line to hide one; editing its installed code, its state in `.codehere/local/`, the approvals file in the user's config folder, or the agent's hook settings outside the repo; deleting or moving `.codehere/` (the hooks then find no Codehere folder and stay silent; its config and rules are tracked, so the deletion is in the diff a person reads); a process that kills or stalls the hook (the result is no line, never a false ✓).
- **Code outside the work tree** that the tests load: global packages, the language runtime, files under the user's home folder.
- **How much a passing test checks.** The scan looks for known ways to weaken tests (measured on CheatBench, `docs/evidence/2026-11-13-cheatbench.md`). A weakening it has no pattern for is a gap in detection, measured separately; this promise is about every changed file being read. Known gaps today: an assertion spread over several lines is compared on its matcher (flipped or weakened), not on its call or its values (so `expect(total(items)).toEqual({` changed to `expect(total(items, { skipTax: true })).toEqual({`, or `toEqual({` to `toEqual(expect.objectContaining({`, is not read; its arguments dropped entirely, `toThrow(` to `toThrow()`, are), and a call-style one (`assert.deepStrictEqual(result, {`, `self.assertEqual(`) is not compared at all; a case dropped from a list on a line that holds a whole assertion (`expect(sortNums([3, 1, 2])).toEqual([1, 2, 3])`), or from a list of names rather than values; an expected value changed while a new test added right below repeats the old line, which git's diff shows as lines added and none removed; an assertion whose old and new lines git's diff puts in different hunks (tests wrapped, or a test added, in the same change); an expected value changed in a table row written on one line (a pytest parametrize tuple, a `test.each` row, a Go row with `want:`); a value changed in a test that shares its name with a new test, when its name line also changed (re-indented, wrapped or edited) and neither the line above the test nor the line after its name tells it from the new one, or when tests of one name are reordered and git puts the old and new line in different hunks, or when one of them is deleted and the rest are wrapped (which test is which is read from the names, where they sit in the diff, and the lines above and after each name); a row removed from a test table written over several lines, or a case dropped from a parametrize list wrapped over several lines; a skip made inside a test's body (`t.skip()`, `pytest.skip()`), a skip a conftest hook adds (`add_marker`), `pytestmark` written over several lines, `xfail`, jest's `test.failing`, playwright's `test.fixme`, and pytest's `-m` marker filter; tox's `{[section]commands}` substitution; a failing test moved into a `describe.skip` block that already exists; a filter moved from one tox env to another when only one env is approved, or from one command to another in the same env; a test path removed from a test command; `--exclude` given to mocha, vitest or cargo, `exclude:` in `.mocharc`; tox `commands` in `setup.cfg`, a `{posargs:...}` default, and `PYTEST_ADDOPTS` set in `setenv`; vitest's `test.exclude` (the same key names coverage files); pytest's `testpaths`, jest's `testMatch` and `collect_ignore` in a `conftest.py` narrowed; tox's `- pytest` prefix and `ignore_outcome`; a filter key written as a shorthand property (`{ testPathIgnorePatterns }`); a CI workflow's trigger changed so it no longer runs on a push; a CI job switched off whose test command lives elsewhere (GitLab `extends:` or an anchor, a GitHub job that calls a reusable workflow, GitLab `workflow: rules:`, Azure `condition: false`). A CI step or job switched off (`continue-on-error`, `allow_failure`, `if: false`, GitLab's `when: manual` or `never`, Azure's `continueOnError` or `enabled: false`) is read. The audit has no file to read, so it reads configs line by line: a line added inside a wrapped list or `addopts` block, with its key on an unchanged line, is not read there. A line longer than 10,000 characters is read in overlapping pieces, so one match across two pieces can be missed. In a CI step, a package or build tool (`npm`, `pnpm`, `turbo`, `gradle`, `mvn` and the like) counts as running the tests only when `test` (or its build word) comes within 200 characters of it.
- **What the record does not walk:** `.git`, `.codehere`, `node_modules` and `site-packages`; a folder holding its own `.git` or a `pyvenv.cfg` that held no test file at session start (a nested repo, a worktree, a virtual environment); and the folders git ignored at session start. Test code git ignores by its own name at session start is not recorded, as an ignored folder is not. A new file in a folder git ignores, and new test code git ignores by its own name, is not read, before the test run or during it; the ignore rules as they are at the finish check decide this, so an ignore line added in the session counts too. These files are let off because builds and installs put them there (a build copying the tests, writing package files, copying a config or writing next to the sources; an install). They are not harmless: where the runner loads every test file into one process (pytest, mocha), a new test file can change what the other tests run against. Hiding a test file this way is working against Codehere (above). A new test config or setup file git ignores by its own name, such as a `pytest.ini` listed in `.git/info/exclude`, is read. Tests the approved command runs straight from such a folder (`node --test dist/test`, with the build a separate step) are read only as their source: an edit made in the build output itself is not read. A repo with more than 200,000 entries outside these folders gets no record: the finish check says so and prints no ✓.

## Honest work

The promise has a second side: honest work is not sent back and gets its ✓. A false send-back, or a ✓ withheld from an ordinary session, is a finding too, rated by how often an ordinary session would meet it.

Known false send-backs today: a new jest or playwright project, or a new tox env, that copies an ignore another one has; a tox pytest command split into two that both keep its filter; a filter narrowed (a `-k` with fewer terms, a path narrowed to a subfolder or a single test, terms reordered inside brackets); a line holding a skip that the agent edits or moves, such as a renamed test or an `it.skip` re-indented into a new `describe` (a moved skip, `continue-on-error` or runner check is read where it lands, since it can switch off something new there; only an assertion that moved is let off, and one that cannot fail only when no assertion left the file); an assertion made stronger (`toBeTruthy()` to `toBe(true)`, `toEqual` to `toStrictEqual`), which is read as changed; a value set outside any test (`const expected = 42;` at the top) moved into its test while a new test above sets the same name; tests of one name reordered and wrapped beside a new group of that name, where git's diff lines up a moved name line with a new one; and a shared object of ignores written out into each project. Each value counts by the places that set it, so the new place reads as a value added; a rule that let new places copy values let a filter spread to tests that ran without it (round 18), so there is none. The agent is sent back once and can say why in one line.
